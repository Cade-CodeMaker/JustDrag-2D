# app/ — 浏览器端编辑器

导入立绘 → 抠图 → 调区域 → 导出 `demo.html`，全程在浏览器里完成，图片不出本机。
原本需要 `tools/` 一串命令加手改 JSON 的流程，现在都在一个界面里。

**当前状态：第 1~5 步全部打通。** 抠图端口与导出端口都对着 Python 侧做过逐字节/逐像素的验证。

## 跑起来

前端不需要单独的环境 —— **Node 也来自项目那个 conda 环境**（见根目录 [README.md](../README.md) 的「环境」）：

```bash
conda activate justdrag     # Python 管线 + Node 都在里面
cd app
npm install                 # 顺带跑 scripts/sync-ort.mjs
```

模型不进仓库，需要放到 `public/models/`（跑过一次 `tools.cutout` 就已经缓存在 `~/.u2net/`）：

```bash
cp ~/.u2net/isnet-anime.onnx app/public/models/
npm run dev                 # http://localhost:5173
```

四个步骤：**导入**（拖入 / 选文件 / Ctrl+V）→ **抠图**（首次要下 168MB 模型，之后浏览器缓存）
→ **调整**（拖椭圆和红色枢轴点）→ **导出**。项目自动存在 IndexedDB 里，关掉标签页再打开会接着上次。

第 4 步除了 `demo.html` 还能导出一张**循环 GIF**，用来直接把效果发给别人看。

## 编辑模型

**一个部位 = 一个枢轴 + 若干个椭圆**，部位是任意长的有序列表（加几个都行，头/腿/胸只是默认模板
里的三个）。枢轴是那个**不动点**：位移 ∝ 到枢轴的距离，所以枢轴本身永远不动 —— 把它放在关节上，
过渡就是数学自动保证的，不需要任何手工羽化。

**运动单元是椭圆，不是部位。** 每个椭圆带自己的**幅度 / 速度 / 滞后**，所以同一部位里的两个椭圆
可以错开摆 —— 这就是「两条腿不要齐步走」要的东西。部位自己的幅度/速度只做两件事：新椭圆继承它，
以及部位分组里的滑块**批量写入**该部位的所有椭圆。

| 画布上的记号 | 含义 |
|---|---|
| 红色十字 | 枢轴。拖动它移动该部位的旋转中心 |
| 悬停 / 选中枢轴 | 显示标签，告诉你这个枢轴属于哪个部位 |
| 椭圆的两圈线 | 外圈是衰减带外沿（权重 0），内圈是核心（权重 1），中间是渐变 |
| 椭圆里那条短线 | **朝向参考**。椭圆是对称的，转四分之一圈看起来一样；这条线 `rot = 0` 时竖直向上，跟着旋转走。不选中的画得细而暗，选中的加粗并带圆头 |

> 这条参考线画的是椭圆的局部 **−y**（屏幕向上）。坐标系 y 向下，所以局部 +y 是朝下的 ——
> 参考线要指「头朝哪」，不能拖一条尾巴在后面。

## 导出 GIF

| | |
|---|---|
| 尺寸 | 256 / 384 / 512 / 768，方形 |
| 帧率 | 10 / 12.5 / 20 / 25 fps —— 只有能整除 100 的帧率，延迟才是整数厘秒，播放速度才不偏 |
| 时长 | 2 ~ 10 秒 |
| 背景 | 深色 / 浅色（棋盘是编辑器用的，不进 GIF） |
| 抖动 | 默认开 |

实测体积（10fps / 5s，浅色背景，仓库里的 `sample` 素材）：

| 尺寸 | 抖动开 | 抖动关 |
|---|---|---|
| 256px | 1.28 MB | 1.14 MB |
| 384px | 2.63 MB | 2.28 MB |
| 512px | 4.34 MB | 3.66 MB |
| 768px | 9.04 MB | 7.23 MB |

**抖动只贵 19% 左右**，比预想的翻倍小得多 —— 背景是整片纯色，LZW 在抖动噪声下照样压得很好。
而关掉抖动后角色皮肤的渐变会出现肉眼可见的色带轮廓。所以默认开着。要是嫌大，先降尺寸，
512 → 384 就能砍掉 40%。

**循环接缝**由导出时自动挑的「从动画的哪一瞬间开始录」的相位决定，**不改你调好的任何参数**，
预览也不受影响。原理写在 `src/pose.js` 的 `bestStartPhase` 注释里：每个椭圆的接缝在
`spd·T ∈ ℤ` 时恒为 0；否则它的目标函数在一个周期上均值为零，必有零点。

能压到多低取决于**滞后怎么配**，这一点值得说清楚：

- **所有椭圆共享同一个滞后**（默认素材 `sample` / `new1` 就是这样）→ 各椭圆的零点落在同一相位上，
  一个起始相位能同时归零，实测 `2.3e-9°`，是机器精度。
- **给了不同滞后** —— 也就是「两条腿别齐步走」想要的效果 —— 零点就错开了，一个相位压不平全部。
  编辑器里的默认模板（头部滞后 0 / 腿部 0.5 / 胸部 0.35）实测残留约 `1.2°`。

两种情况下状态行都**如实报出实际残差角度**，不假装无缝。想回到无缝，把同一部位里（以及同速度的
部位之间）的滞后调成一致即可。

**取景只保证「画面完整」。** 取景方框是 `min(w,h) × 缩放`，方框里就是整张立绘 —— 所以
**缩放超过 100% 时，方框比窗口大，着色器只能裁掉角色的四边**（`core/deform.glsl:29` 的边界
判断）。预览窗口比方框宽，勉强还能保住左右、只丢上下；**方形 GIF 没有这份余地**，照裁就是
四边全丢，出来的是一张「只剩角色中间一块」的动图 —— 这正是原先的 bug。

所以导出按 `fitZoom()` 取景：**100% 以下照旧**（那是你要的留白），**100% 以上不再放大**，
取景到放得下为止。也就是说 GIF 里的角色永远和「缩放 100%」时一样大、一样完整，状态行会
写明这一次按 100% 取了景。

> 为什么不干脆做成分辨率跟随比例（导出你现在看到的那个长方形）？那会让 GIF 的尺寸随浏览器
> 窗口大小浮动，同一个项目换台机器导出就是另一个文件；而且 `zoom > 1` 时那个长方形本身
> 已经裁掉了角色的上下。宁可固定成方形、永远不丢内容。

GIF 只有 256 色，这是格式本身的限制，不是实现缺陷。想要更好的质量应该换 WebM/APNG —— 那是
另一件事，交付物 `demo.html` 保持零依赖不变。

## 验证

```bash
python -m tools.build_demo new1           # 导出比对的基准
python app/test/dump_reference.py sample  # 抠图比对的基准
cd app
npm test                # pose + gif 是纯 Node，秒级；matting + ui 要开浏览器
```

`test/pose.test.js` 和 `test/gif.test.js` **不需要浏览器也不需要模型** —— 前者是纯数学，
后者喂合成帧给编码器。所以它们可以在每次改动后无脑跑，穷举那些用肉眼看不出来的东西
（接缝扫 2000 个相位、每一帧的延迟、抖动开与关的字节）。

`test/ui.test.js` 分五段：

| | 查什么 |
|---|---|
| A. 界面 | 真按那套控件走一遍导入 → 抠图 → 加椭圆，检查状态确实跟着变；并在权重视图里读回一个像素，确认它用的是该部位自己的颜色 |
| B. 导出 | 拿 `assets/new1` 的三份输入，让**浏览器**构建一遍，和 `tools/build_demo.py` 产出的文件比对 |
| C. 产物 | 把浏览器构建出来的文件用 `file://` 打开，确认它真的画出了东西 |
| D. 重开 | 冷启动一次，确认项目从 IndexedDB 里完整恢复 |
| E. GIF | 翻行是否正确、真导出一张并按块解析、`zoom<1` 那圈补色、`zoom>1` 有没有裁掉四边 |
| F. 上限 | 这台设备能驱动几个椭圆、两个天花板里谁先到顶 |

B 是关键那条：它把导出的正确性从"看起来对"变成"和 Python 一模一样"。

E 里那条翻行检查值得单独说：它**不会**拿角色的图去比（没法判断角色"应该"朝哪边），
而是临时换上一张上半红下半蓝的贴图、把形变归零，再问红色跑到了哪一头。忘了翻行是一条
静默的 bug —— 出来的是一张倒立的角色，而任何"和参考帧比对"的测试都会跟着一起倒，
照样通过。

## 五个非显然的坑

**1. `normalize()` 除以的是图像自身的最大像素值，不是 255。**
rembg 写的是 `im_ary / max(np.max(im_ary), 1e-6)`。白底图恰好等于 /255，所以"顺手改成
/255"在大多数图上都是对的 —— 这正是它危险的地方。

**2. std 是 `(1,1,1)`，不是 ImageNet 的 `(0.229,0.224,0.225)`。**
`U2netSession` 传 ImageNet std，`DisSession`（也就是 `isnet-anime`）不传。用错照样出
一张看着合理的 mask，只是不是同一张。

**3. ORT 的 `.wasm` 不能放在 `public/` 里被 `import()`。**
Vite 明确禁止源码 import `public/` 下的文件，而 ORT 正是用动态 import 去取 wasm 的。
失败信息是 `expected magic word 00 61 73 6d, found 3c 21 64 6f` —— 那是 `<!do`，
即 Vite 的 SPA 兜底把 `index.html` 喂给了 `WebAssembly.instantiate`。
`vite.config.js` 里的 `serve-ort-runtime` 中间件在 Vite 的转换中间件之前把文件直接
吐出去，绕开整条管线。

**4. 编辑器读 `core/` 和 `tools/` 里的源文件，所以 Vite 必须被允许往上走。**
导出的 demo 是把 `tools/template.html` + `core/region_field.js` + `core/deform.glsl`
拼出来的，浏览器里要做同一件事，就得拿到同样的字节（`?raw` 导入）。默认 dev server
只允许 `app/` 以内的路径，会直接 403 —— `server.fs.allow` 就是为这个设的。
`region_field.js` 是 UMD-lite、在浏览器里给 `self` 赋值而不是返回，所以它是**求值**
而不是 `import`；这样编辑器和导出产物跑的才是同一份权重场。

**5. JS 的 `String.replace` 把 `$` 当特殊字符，Python 的 `str.replace` 不。**
所以每一处替换都传函数而不是字符串。否则用户 `_comment` 里或着色器源码里的一个
`$'` 会被悄悄展开成模板内容 —— 而 `build_demo.py` 不会有这个问题。

## GIF 导出里四个静默的坑

**1. `readPixels` 是自下而上的，GIF 的行是从上往下的。** GL 原点在左下。仓库里原有的两处
`readPixels`（`verify/compare_equivalence.js`、`ui.test.js`）都没翻 —— 因为它们两边都是自下而上，
翻转互相抵消了。导出这里**没有东西可以抵消**，忘了翻就是一张倒立的角色。
`test/ui.test.js` E1 用一个红蓝对半的合成贴图钉死这件事。

**2. `zoom < 1` 会留一圈透明，而 GIF 没有 alpha。** 着色器在取景方框外直接
`gl_FragColor = vec4(0.0)`（`core/deform.glsl:29`），那圈读出来是 `a == 0`，进 GIF 会变成
**黑边**。抓帧后按 `a == 0` 补背景色 —— 用 alpha 判断而不是在 JS 里重算方框边界，是因为
重算一旦差一个像素就是一条 1px 黑线，而 alpha 是着色器自己的裁决。

**3. 预览的取景方框不是导出的画幅。** 方框是 `min(w,h)×zoom`，`zoom > 1` 时它比窗口大，
着色器于是把 `zoom` 变成了「裁掉中间 1/zoom 以外的部分」。预览的窗口比方框宽，看起来还好；
方形导出就是那个方框本身，一裁就是四边全丢 —— **导出必须用 `fitZoom` 取景，不能用
`params.zoom`**。`pose.test.js` C 段把整条滑块范围 × 四种尺寸都扫了一遍，断言方框一定装得下；
`ui.test.js` E4 拿一张四边都是品红的贴图做因果检查（裁了边就看不见品红），把 `fitZoom`
改回恒等函数立刻两红。

**4. 背景色不要照抄着色器里的十进制常量。** `deform.glsl:61` 写的是 `vec3(0.90)`，
看着像 230，实际是 **229** —— 0.90 在 float32 里是 0.89999997…，乘 255 得 229.4999…，
四舍五入到 229。硬编码 230 会在方框边缘留下一条 1/255 的接缝，而大片纯色正是这种差值
唯一看得见的地方。现在这个颜色是**从渲染结果里读回来的**（`stage.js` 的 `bgColorOf`）。

## 下一步

1. **把 `bleed` 挪到 GPU** —— 它现在是全流程 68% 的耗时（273ms），而推理只用 97ms。
   8 次迭代的 8 邻域扩散是个现成的 ping-pong fragment shader pass。
2. **`ort.env.wasm.wasmPaths = '/ort/'` 是写死的根路径。** 部署到子路径下会取不到
   wasm。Tauri 里无所谓，放到线上要改成相对路径。
3. **非正方形立绘会被拉伸成正方形。** 着色器把 `[0,1]²` 直接当 uv 用，`uZoom` 框的是
   `min(w,h)` 的正方形。现在的素材都是 1024×1024 所以看不出来，但 3:4 的立绘会变形 ——
   这是**交付产物本身**的行为，改它要动着色器和导出，不只是界面。
4. **WebView2 的 WebGPU 可用性** —— 决定 Tauri 外壳里的速度能否和浏览器持平。
5. **界面框架** —— 现在是原生 DOM。Vue 的结论是**暂时不换**：这一轮把编辑能力从
   `tools/template.html` 拆进 `app/` 时，原生 DOM 完全扛住了（多部位列表、检视面板、
   增删改都是几十行的事），换框架的收益还抵不上它带来的构建与心智成本。
   要换的前提是编辑逻辑本身再复杂一个量级 —— 而且不管怎么换，**交付物
   `tools/template.html` 必须保持零依赖 vanilla**，Vue 只能属于开发期编辑器。
